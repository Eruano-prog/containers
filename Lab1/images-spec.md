# Контракт образов Lab 1

Статус: контракт и [план выполнения](part6-plan.md) согласованы пользователем. Dockerfile, Dockerfile.single, go.mod, .dockerignore и [инструкция](part6-images.md) подготовлены; удалённые сборки и запуски ещё не проверены.

## Исходные данные

Удалённый Debian amd64: Go 1.24.4. Фактический go.mod пользователя:

~~~go
module main

go 1.24.4
~~~

HTTP-контракт сервиса остаётся прежним: /health, /eat?mb=N, /burn, порт 8080.

## Планируемые файлы

- go.mod — точная копия модуля с удалённого устройства, чтобы сборка из репозитория имела те же входные данные.
- Dockerfile.single — одна стадия на golang:1.24.4; компилятор, исходники и служебные файлы сборки остаются в конечном образе.
- Dockerfile — multi-stage: сборщик на том же golang:1.24.4, конечная стадия scratch, в которую копируется только бинарник.
- .dockerignore — ограниченный контекст сборки с main.go, go.mod и Dockerfile-файлами; отчёт, скриншоты, скрипты и бинарники хоста в контекст не входят.
- part6-images.md — команды пользователя для сборок, проверки HTTP, сравнения размеров, файловых слоёв и повторной сборки.
- Lab1.md — фактические результаты, заполняемые по выводу пользователя.

## Поведение сборок

Обе сборки компилируют один main.go с одинаковыми параметрами: CGO_ENABLED=0 и go build -trimpath. Оба образа запускают /lab1-serv напрямую, без shell-обёртки, от UID/GID 1000:1000 и слушают 8080. Статическая сборка нужна для работы в scratch без libc и динамического загрузчика.

Теги результатов: lab1-api:single и lab1-api:multi. Метаданные EXPOSE 8080 описывают порт, публикация задаётся при docker run.

В scratch не добавляются shell, пакетный менеджер и инструменты отладки. Для данного HTTP-сервиса дополнительные файлы и сертификаты не нужны. Эксперимент записи файлов позднее будет выполнен на обычном образе, где есть shell, без добавления новых HTTP-endpoint.

## Проверка

Все сборки, запуски и команды выполняет пользователь на удалённом Debian.

1. Собрать оба образа и проверить /health у каждого.
2. Получить фактические размеры, ID образов, число RootFS.Layers и историю сборки.
3. Повторить сборки без изменения исходников; сохранить подтверждение использования кэша.
4. После проверки понимания перейти к потере файла при пересоздании контейнера и сохранению в named volume.

Доступность тега golang:1.24.4, используемый builder, размеры и результаты запусков пока не подтверждены. При ошибке получения образа или сборки сначала исследовать фактический вывод, а не менять версии молча.

Источник механизма multi-stage: https://docs.docker.com/build/building/multi-stage/
